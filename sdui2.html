Hybrid Architecture: Server-Driven Canonical UI with Generative Rhetorical On-Ramps

calendar_today December 2025 person Sridhar Dhulipala, UIDAI

Executive Summary

This document proposes a hybrid architecture that cleanly separates:

  1. Canonical Layer: Server-Driven UI (SDUI) — deterministic, auditable, legally certifiable
  2. Rhetorical Layer: Generative AI with SLMs — contextual, adaptive, personalized on-ramps

"The key insight: AI doesn’t generate the form; AI generates the journey TO the form."

Users enter through contextually-appropriate rhetorical experiences generated by SLMs, then seamlessly segue into canonical SDUI for formal data collection. This preserves regulatory guarantees while enabling billion-scale personalization.

Part 1: The Architectural Insight

1.1 The Problem with Full Generative UI

Previous iterations of the Token Observatory architecture proposed AI-generated UI for the entire journey. This creates challenges:

Challenge Risk
AuditabilityHow do you audit a UI that’s different for every user?
CertificationRegulators need to certify a specific UI, not a generative process
TestingCan’t exhaustively test infinite UI variations
Legal liabilityWhich generated variant is the “official” one?
ReproducibilityUser disputes require reproducing exact UI they saw

Part 2: Server-Driven UI for Canonical

2.1 What is Server-Driven UI?

Server-Driven UI (SDUI) is an architectural pattern where:

  • The server sends a declarative specification of what UI to render
  • The client interprets the specification and renders native components
  • UI changes require no app updates — just server-side changes

Adopted by: Netflix, Airbnb, Spotify, Shopify, Lyft

2.2 Why SDUI for Canonical?

PropertySDUI Advantage
DeterministicSame spec → same UI, always
AuditableSpec is a JSON/protobuf document that can be versioned, signed, logged
CertifiableRegulators can certify a specific spec version
ReproducibleStore spec with transaction → can reproduce exact UI user saw
CacheableSpecs can be cached at CDN, CSC, device
Offline-capablePre-download specs for offline operation
TestableFinite set of specs can be exhaustively tested
Update without releaseFix UI issues without app store deployment

Part 4: The Segue Architecture

4.1 Defining the Segue Point

The segue point is where rhetorical hands off to canonical. It is the architectural primitive that connects the adaptive world to the deterministic world.

The Segue Point

"तैयार हैं? चलिए शुरू करते हैं।"
(Ready? Let's begin.)

4.2 Segue Implementation

interface SegueController {
  async initiateSegue(context: RhetoricalContext, journeyId: JourneyId): Promise {
    // 1. Log rhetorical session (telemetry)
    this.telemetry.log(context);
    
    // 2. Resolve & Validate Canonical Spec
    const spec = await this.resolveCanonicalSpec(journeyId);
    if (!this.validateSpec(spec)) throw new Error("Invalid Spec");
    
    // 3. Handover to Renderer
    this.canonicalController.beginJourney(spec);
  }
}

Part 5: Error Handling Architecture

Rhetorical Errors

Scenario: SLM generates invalid content.

  1. Log error
  2. Skip remaining rhetorical content
  3. Display static fallback message
  4. Proceed directly to canonical SDUI

Canonical Errors

Scenario: Backend timeout.

  1. EXIT to rhetorical layer
  2. SLM generates compassionate explanation
  3. SLM guides user on next steps
  4. RE-SEGUE back when ready

Part 9: Conclusion

The Promise

A user in rural Tamil Nadu opens the Aadhaar app.

An SLM generates a warm welcome in Chennai Tamil, explains what they’ll need, reassures them their data is safe, and says "Ready? Let’s begin."

They tap the button.

The SDUI renderer displays the exact same certified form that a user in Delhi sees—but localized to Tamil. The rhetorical journey was unique. The canonical completion was universal.

That’s the hybrid promise: personalized approach, standardized completion.
