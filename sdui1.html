Hybrid Architecture: Server-Driven Canonical UI with Generative Rhetorical On-Ramps

Document Version: 4.0
Date: December 2025
Author: Sridhar Dhulipala, Principal Design Advisor, UIDAI

Executive Summary

This document proposes a hybrid architecture that cleanly separates:

  1. Canonical Layer: Server-Driven UI (SDUI) — deterministic, auditable, legally certifiable
  2. Rhetorical Layer: Generative AI with SLMs — contextual, adaptive, personalized on-ramps

The key insight: AI doesn’t generate the form; AI generates the journey TO the form.

Users enter through contextually-appropriate rhetorical experiences generated by SLMs, then seamlessly segue into canonical SDUI for formal data collection. This preserves regulatory guarantees while enabling billion-scale personalization.

Part 1: The Architectural Insight

1.1 The Problem with Full Generative UI

Previous iterations of the Token Observatory architecture proposed AI-generated UI for the entire journey. This creates challenges:

Challenge Risk
Auditability How do you audit a UI that’s different for every user?
Certification Regulators need to certify a specific UI, not a generative process
Testing Can’t exhaustively test infinite UI variations
Legal liability Which generated variant is the “official” one?
Reproducibility User disputes require reproducing exact UI they saw

1.2 The Hybrid Solution

Part 2: Server-Driven UI for Canonical

2.1 What is Server-Driven UI?

Server-Driven UI (SDUI) is an architectural pattern where:

  • The server sends a declarative specification of what UI to render
  • The client interprets the specification and renders native components
  • UI changes require no app updates — just server-side changes

Adopted by: Netflix, Airbnb, Spotify, Shopify, Lyft

2.2 Why SDUI for Canonical?

Property SDUI Advantage
Deterministic Same spec → same UI, always
Auditable Spec is a JSON/protobuf document that can be versioned, signed, logged
Certifiable Regulators can certify a specific spec version
Reproducible Store spec with transaction → can reproduce exact UI user saw
Cacheable Specs can be cached at CDN, CSC, device
Offline-capable Pre-download specs for offline operation
Testable Finite set of specs can be exhaustively tested
Update without release Fix UI issues without app store deployment

│                                                                                 │
│  1. DETERMINISM                                                                 │
│     Given: User context C, Journey J, Screen S                                 │
│     Then: SDUI_spec(C, J, S) = constant                                        │

│                                                                                 │
│  2. AUDITABILITY                                                                │
│     Every transaction stores:                                                   │
│     - Journey ID + version                                                      │
│     - Screen sequence traversed                                                 │

│     - Timestamp and duration per screen                                        │
│     Auditors can reproduce EXACT UI user experienced                           │
│                                                                                 │
│  3. CERTIFICATION                                                               │
│     Each SDUI spec version is:                                                  │
│     - Reviewed by legal/compliance                                              │
│     - Tested exhaustively                                                       │
│     - Signed by UIDAI Canonical Authority                                      │
│     - Published with validity period                                            │
│     Regulators certify the SPEC, not the rendering                             │
│                                                                                 │
│  4. IMMUTABILITY                                                                │
│     Once published, a spec version is NEVER modified                           │
│     Bug fixes create NEW version with NEW certification                        │

│                                                                                 │
│  5. NON-BYPASSABILITY                                                           │
│     Transaction cannot complete without traversing canonical SDUI              │

4.2 Segue Implementation

interface SegueController {
  
  /**
   * Called when rhetorical preparation is complete.
   * Transitions user to canonical SDUI flow.
   */
  async initiateSegue(
    rhetoricalContext: RhetoricalContext,
    targetJourney: JourneyId
  ): Promise<void> {
    
    // 1. Log rhetorical session (non-blocking, best-effort)
    this.telemetry.logRhetoricalSession({
      sessionId: rhetoricalContext.sessionId,
      duration: rhetoricalContext.duration,
      language: rhetoricalContext.language,
      slmUsed: rhetoricalContext.slmId,
      contentGenerated: rhetoricalContext.contentHashes
    });
    
    // 2. Resolve canonical SDUI spec
    const sduiSpec = await this.resolveCanonicalSpec(targetJourney, {
      preferredLanguage: rhetoricalContext.language,
      deviceCapabilities: rhetoricalContext.device,
      accessibilityNeeds: rhetoricalContext.accessibility
    });
    
    // 3. Validate spec signature and version
    if (!this.validateSpec(sduiSpec)) {
      throw new CanonicalSpecInvalidError();
    }
    
    // 4. Initialize canonical renderer
    const renderer = this.getRenderer(sduiSpec.renderingHints);
    
    // 5. Begin canonical flow
    await renderer.renderScreen(sduiSpec.screens[0]);
    
    // 6. Transfer control to canonical flow controller
    this.canonicalController.beginJourney(sduiSpec, {
      rhetoricalSessionId: rhetoricalContext.sessionId,
      entryPoint: 'rhetorical_segue',
      preparedContext: rhetoricalContext.inferredContext
    });
  }
  
  /**
   * Fallback: Skip rhetorical entirely, go straight to canonical.
   * Used when SLM unavailable or user opts out of guidance.
   */
  async directToCanonical(targetJourney: JourneyId): Promise<void> {
    const sduiSpec = await this.resolveCanonicalSpec(targetJourney);
    const renderer = this.getRenderer(sduiSpec.renderingHints);
    await renderer.renderScreen(sduiSpec.screens[0]);
    
    this.canonicalController.beginJourney(sduiSpec, {
      entryPoint: 'direct',
      preparedContext: null
    });
  }
}

Part 9: Conclusion

9.1 The Core Insight

The hybrid architecture separates what MUST be controlled from what CAN be personalized.

  • Canonical SDUI: Must be controlled — deterministic, auditable, certified
  • Rhetorical AI: Can be personalized — adaptive, contextual, forgiving of variation

This separation enables billion-scale personalization without sacrificing regulatory guarantees.

9.2 The Segue as Architectural Primitive

The segue point is the key abstraction:

  • Clear handoff from adaptive to deterministic
  • AI prepares, SDUI executes
  • Personalization on-ramp, standardized completion
  • Failure in rhetorical doesn’t affect transaction
  • Audit trail is clean (SDUI spec + user inputs)

9.3 Why This Works for Aadhaar

Aadhaar Requirement How Architecture Satisfies
Serve 1.4B diverse users Rhetorical layer adapts to context
Legal compliance Canonical SDUI is certifiable
Audit requirements SDUI spec stored with transaction
Offline operation SDUI specs cacheable; rhetorical optional
Multiple languages Both layers support multi-language
Accessibility Both layers support accessibility features
Trust building Rhetorical layer provides human-centric guidance
Data integrity Canonical SDUI enforces field validation

9.4 The Promise

A user in rural Tamil Nadu opens the Aadhaar app.

An SLM generates a warm welcome in Chennai Tamil, explains what they’ll need, reassures them their data is safe, and says “Ready? Let’s begin.”

They tap the button.

The SDUI renderer displays the exact same certified form that a user in Delhi sees—but localized to Tamil, with the same validation rules, the same fields, producing the same API payload.

The rhetorical journey was unique. The canonical completion was universal.

That’s the hybrid promise: personalized approach, standardized completion.
