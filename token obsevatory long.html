Token Observatory Studio

Technical Proposal for Adaptive UI Architecture at Population Scale

Document Version: 1.0 Date: December 2025 Author: Sridhar Dhulipala, Principal Design Advisor, UIDAI Classification: Internal Discussion Document

Executive Summary

This document proposes the establishment of the Token Observatory Studio—a research and engineering lab focused on developing adaptive UI architecture for population-scale digital systems. The core problem: how do we maintain canonical compliance in identity transactions while allowing the UI layer to adapt to the diverse contexts of a billion users?

The proposed architecture introduces a "Token UX" abstraction layer where interface components carry context metadata. A generation layer composes these tokens into journey variants at runtime, while a validation loop ensures every generated path terminates in a canonical, system-compliant transaction.

Key Proposition: Design ~180 primitives. Generate millions of contextually-appropriate journeys. Serve a billion users—each receiving one journey matched to their context—with every journey landing in the same canonical, compliant transaction.

1. Problem Statement

1.1 The Current Trade-off

Digital Public Infrastructure (DPI) currently optimizes for Distribution Reach. To achieve this scale, user journeys are standardized ("Canonical"), forcing users to adapt to the system.

Conversely, high-touch solutions offer User Relevance but cannot scale beyond small cohorts due to manual design constraints.

1.2 The Relevance Wall

Current systems hit a "Relevance Wall." One fixed user journey cannot accommodate the diverse contexts of a billion users:

[Image of diversity in Indian population demographics chart]
Context Dimension Variance in Indian Population
Language 22 scheduled languages, 100+ dialects
Literacy Pre-literate to expert digital users
Device Feature phones to high-end smartphones
Connectivity Intermittent 2G to 5G broadband
Accessibility Visual, motor, cognitive impairments
Assistance Mode Self-service to fully assisted

This results in drop-offs at the "last mile" of interaction—users who have the right to access services but cannot navigate the standardized interface.

1.3 The Target State

Quadrant Characteristics Example
Fragmented Utilities Low Touch, Low Scale Legacy Systems
Current DPI Low Touch, High Scale Standardized Portals
Boutique Design High Touch, Low Scale Concierge Banking
Intelligent UX (Target) High Touch, High Scale Generated Contextual Interfaces

2. Proposed Architecture

2.1 Core Concept: Decoupling Business Logic from User Interface

The architecture separates:

  • Canonical Layer (The Constraints): Fixed rules, validation requirements, API schemas, regulatory compliance—immutable regardless of user context
  • Intelligent UX Engine (The Generator): Takes user context and canonical constraints as input, produces contextually-appropriate interface as output
  • Rhetorical Layer (The Experience): Dynamic interfaces that adapt to user context while strictly adhering to canonical requirements

2.2 Three-Engine Architecture

├─────────────────────┬─────────────────────┬─────────────────────────┤

│  Context Inference  │  LLM + RAG + MCP    │  Canonical Coordination │

│ • Session replay    │ • Large Language    │ • Rules-based execution │
│ • Behavioral        │   Models            │ • API transactions      │

│                     │   responses         │   gates                 │
└─────────────────────┴─────────────────────┴─────────────────────────┘

2.3 Token Space vs. Pixel Space

Aspect Token Space (Probabilistic) Pixel Space (Deterministic)
Reality Synthetic Physical
UX Type Perishable, Rhetorical Permanent, Canonical
Learning Observational (user context, journey patterns) Derived Specifications (system rules, defined journeys)
Flexibility Adaptive to context Fixed implementation

The Shift: Instead of crafting pixels (Pixel Space), we craft logical tokens (Token Space). The AI handles the "last mile" rendering, ensuring the interface matches the user's mental model while strictly adhering to system rules.

4.4 Error 404 (Page Not Found): Rhetorical Variations

4.4.1 Rural User Response

Token Selection Logic:

IF device = feature_phone AND literacy_signal < 3:
    ACTIVATE: voice_primary, single_action, auto_redirect
    SUPPRESS: technical_details, multiple_options
    INJECT: helpline_prominent, sms_fallback

Rendered Experience:

Element Implementation
Primary Communication Auto-playing voice in Hindi explaining the issue
Error Explanation "The page you wanted is no longer here. Don't worry, I'll take you to the right place."
Action Options Single large button: "Go Home"
Input Modality Voice command accepted ("Ghar" to go home)
Fallback SMS link to correct page sent automatically
Recovery Behavior Auto-redirect to home after 10 seconds

Design Rationale:

  • No technical jargon ("404" never displayed)
  • Single action path reduces cognitive load
  • Voice-first accommodates low literacy
  • SMS fallback addresses connectivity issues

4.4.2 Urban Professional Response

Token Selection Logic:

IF device = desktop/laptop AND literacy_signal >= 4:
    ACTIVATE: multi_option, context_explanation, history_aware
    SUPPRESS: voice_primary, auto_redirect
    INJECT: bookmark_update_hint, search_prominent

Rendered Experience:

Element Implementation
Primary Communication Text notification with context
Error Explanation Specific reason (portal update, outdated bookmark)
Action Options Multiple: Home, Search, Services
Personalization Quick actions based on user history (e.g., "Continue Address Update - draft saved")
Technical Detail Bookmark update hint with correct URL
Recovery Behavior User-directed (no auto-redirect)

Design Rationale:

  • Respects user competence (no hand-holding)
  • Provides context (why this happened)
  • Offers multiple recovery paths (user has agency)
  • History-aware suggestions reduce friction

4.4.3 Senior Citizen Response

Token Selection Logic:

IF age_signal > 55 OR interaction_pattern = hesitant:
    ACTIVATE: reassurance_first, guided_recovery, large_text
    SUPPRESS: technical_details, multiple_simultaneous_options
    INJECT: progress_indicator, physical_fallback, helpline

Rendered Experience:

Element Implementation
Primary Communication Reassuring message: "Don't worry, we'll help you"
Error Explanation Human terms: "The page has moved. This happens sometimes."
Action Options Guided selection: "What were you trying to do?" with clear options
Visual Design Large text, high contrast, clear boundaries
Physical Fallback Seva Kendra location with distance
Recovery Behavior Step-by-step guidance to correct destination

Design Rationale:

  • Emotional acknowledgment before information
  • No blame language
  • Guided recovery reduces decision anxiety
  • Physical fallback provides security

4.4.4 Visually Impaired User Response

Token Selection Logic:

IF accessibility_mode = screen_reader:
    ACTIVATE: sequential_audio, limited_options, multi_input
    SUPPRESS: visual_elements, simultaneous_choices
    INJECT: keyboard_shortcuts, timeout_warning, repeat_option

Rendered Experience:

Element Implementation
Primary Communication Sequential screen reader announcements
Error Explanation "Navigation error. The page was not found. You have two options."
Action Options Maximum 2 options (Home, Help)
Input Modality Multi-modal: voice command OR keypress
Timeout Handling Clear warning with safe default
Repeat Option H key to repeat options

Design Rationale:

  • Sequential announcements (not simultaneous)
  • Limited options reduce memory load
  • Multi-modal input provides flexibility
  • No reliance on visual-dependent information

4.5 Error 503 (Service Unavailable): Rhetorical Variations

4.5.1 Rural User Response

Token Selection Logic:

IF connectivity = low AND literacy_signal < 3:
    ACTIVATE: auto_retry, voice_reassurance, data_safety_prominent
    SUPPRESS: manual_options, technical_eta
    INJECT: sms_notification, offline_queue_if_eligible
    SET: retry_interval = 30s (conserve data)

Rendered Experience:

Element Implementation
Primary Communication Auto-playing voice in Hindi
Key Message "Your work is safe. Service is busy. We'll try again."
User Action Required None (auto-retry)
Visual Feedback Countdown timer with progress bar
Data Safety Explicit confirmation: "Your address is saved"
Fallback SMS notification when service recovers

Design Rationale:

  • Primary anxiety (data safety) addressed immediately
  • User does nothing—system handles retry
  • Longer retry interval conserves mobile data
  • SMS fallback for users who may leave

4.5.2 Urban Professional Response

Token Selection Logic:

IF device = desktop AND literacy_signal >= 4:
    ACTIVATE: transparent_status, multi_alternative, session_transfer
    SUPPRESS: voice_primary, simplified_messaging
    INJECT: technical_details_expandable, status_page_link
    SET: retry_interval = 10s (user has bandwidth)

Rendered Experience:

Element Implementation
Primary Communication Status dashboard with specific information
Key Message "High traffic on authentication servers. ETA: 2-3 minutes."
User Options Continue on mobile (QR transfer), schedule for later, download draft
Technical Details HTTP code, server identifier, status page link
Session Handling Draft preserved, session transferable
User Control Cancel button (respects their time)

Design Rationale:

  • Transparency builds trust
  • Specific ETA (not vague "later")
  • Multiple paths give user agency
  • Session transfer maximizes flexibility

4.5.3 Senior Citizen Response

Token Selection Logic:

IF age_signal > 55 OR needs_guidance = true:
    ACTIVATE: safety_first, progress_visibility, human_explanation
    SUPPRESS: technical_status, multiple_simultaneous_options
    INJECT: specific_helpline_script, dont_close_warning
    SET: retry_interval = 25s

Rendered Experience:

Element Implementation
Primary Communication Safety message in prominent box: "Your information is SAFE"
Key Message "The system is very busy. This is normal."
Progress Visibility Full step-by-step status showing completed vs. pending
User Instruction "Please don't close this page"
Helpline Support Specific script: "Tell them your address update is stuck at Step 4"
Alternative Path SMS when ready (preserves effort)

Design Rationale:

  • Safety message first and prominent
  • Full progress visibility reduces anxiety
  • Human explanation ("busy" not "503")
  • Specific helpline script ensures effective support

4.5.4 Visually Impaired User Response

Token Selection Logic:

IF accessibility_mode = screen_reader:
    ACTIVATE: sequential_priority_announcements, periodic_updates, haptic
    SUPPRESS: visual_progress, countdown_timer
    INJECT: phonetic_spelling_for_ids, single_key_options
    SET: announcement_interval = 30s

Rendered Experience:

Element Implementation
Announcement Priority 1) Safety, 2) Status, 3) Action required
Key Message "Your information is saved. You don't need to do anything."
Periodic Updates Every 30 seconds: "Still waiting. Retry attempt 2 of 3."
Help Access Press H for options
Haptic Feedback Single pulse = retry in progress; Long vibration = completion
Success Confirmation Phonetic spelling of transaction ID

Design Rationale:

  • Prioritized announcement order
  • "You don't need to do anything" reduces anxiety
  • Periodic updates prevent silent waiting
  • Haptic provides non-audio state feedback

5. Scale Validation: Billion Users, Million Journeys

This section validates that "million journeys" is not aspirational language but mathematical necessity.

5.1 The Combinatorial Framework

TOTAL JOURNEY SPACE = Context Combinations × Path Variations × State Branches

5.2 Context Vector Dimensions

Dimension Possible Values Count
Language Hindi, English, Tamil, Telugu, Bengali, Marathi, Gujarati, Kannada, Malayalam, Odia, Punjabi, Assamese, others ~15
Literacy Tier Tier 1 (pre-literate) through Tier 5 (expert) 5
Device Type Feature phone, basic smartphone, advanced smartphone, tablet, laptop/desktop 5
Connectivity Intermittent/2G, 3G, 4G, 5G/Broadband 4
Accessibility Need None, voice-primary, screen-reader, motor-impaired, cognitive-assist 5
User Experience First-time, occasional, regular, expert 4
Assistance Mode Self-service, family-assisted, agent-assisted, kiosk 4
Age Bracket Youth (<25), Adult (25-55), Senior (>55) 3
Time Pressure Relaxed, moderate, urgent 3
Trust State Skeptical, neutral, trusting, evangelist 4

Raw Combinations (if fully independent):

15 × 5 × 5 × 4 × 5 × 4 × 4 × 3 × 3 × 4 = 4,320,000 context combinations

5.3 Context Clustering into Archetypes

Not all combinations are meaningful. Many are:

  • Impossible: Screen-reader + feature phone
  • Redundant: Literacy Tier 5 + needs guidance
  • Indistinguishable: 4G vs. 5G for text-based journey

The system clusters raw combinations into meaningful Context Archetypes:

Archetype Example Represents Approximately
Rural First-Time ~50,000 raw combinations
Urban Professional ~30,000 raw combinations
Senior Citizen ~40,000 raw combinations
Visually Impaired ~20,000 raw combinations

Working estimate: 1,000-2,000 meaningful archetypes

5.4 Journey Path Variations

For Address Update journey (6 canonical steps):

Step Token Variants per Archetype Rationale
Step 1: Enter Aadhaar 3 Numeric pad, voice, scan
Step 2: Authenticate 4 OTP, Face, Fingerprint, Assisted
Step 3: Enter Address 5 Voice, type, GPS, map-pin, scan-doc
Step 4: Upload Document 4 Camera, gallery, skip-if-eligible, assisted
Step 5: Review 3 Full review, summary, voice-readback
Step 6: Confirm 2 Standard, extended-confirmation

Success path combinations per archetype:

3 × 4 × 5 × 4 × 3 × 2 = 1,440 distinct success paths

5.5 Error State Branching

Each step can encounter errors with multiple recovery paths:

Step Possible Errors Recovery Paths per Error
Step 1 Invalid Aadhaar, network timeout 3 each
Step 2 Auth failure, biometric mismatch, OTP expired 4 each
Step 3 Validation error, geocoding failure 3 each
Step 4 Upload failure, file too large, format invalid 4 each
Step 5 Session timeout 2
Step 6 503, 429 (rate limit), payment failure 3 each

Average outcomes per step: 1 (success) + (2 errors × 3 recoveries) = 7

Total paths including errors: 7^6 = 117,649 paths per archetype

5.6 Full Calculation

TOTAL JOURNEY SPACE = Archetypes × Paths per Archetype

Conservative:    1,000 × 117,649 = 117,649,000 (~118 million)
Moderate:        1,500 × 150,000 = 225,000,000 (~225 million)
With edge cases: 2,000 × 200,000 = 400,000,000 (~400 million)

5.7 Practical vs. Theoretical Space

Space Scale Definition
Theoretical ~400 million Every possible path the system could generate
Practical ~1 million Paths that will actually be traversed by real users
Validated ~50,000 Paths tested/observed in production
Designed 4 Archetypes explicitly created

The architecture generates from the 400 million space, but user behavior concentrates in a smaller observed space. "Million journeys" represents the realistic scale of actual usage.

Appendix A: Glossary

Term Definition
Canonical Journey The fixed, deterministic path defined by system rules and regulatory requirements
Rhetorical Journey A contextually-adapted path that varies based on user context while adhering to canonical constraints
Token (UI Token) An abstraction of a UI element that carries context metadata enabling adaptive rendering
Context Vector A multi-dimensional representation of user context (device, language, literacy, etc.)
Archetype A cluster of similar context vectors that share UX requirements
Token Space The probabilistic, adaptive layer where tokens are composed into journeys
Pixel Space The deterministic, canonical layer of fixed system rules and UI specifications
